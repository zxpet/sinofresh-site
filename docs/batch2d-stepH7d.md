## 0. 本批形状：`mode: symmetric`（第三种方向）

H7a／H7b 是 `insert`（批次改写基线已有的字符串 ⇒ 期望页可以从基线**造**出来），
H7c 是 `delete`（新增内容的**每个字节都是按记录变的** ⇒ 只能把声明区从候选里拿掉，
要求余下部分等于基线）。H7d 两件事同时发生：**从参数列表里删掉 6–7 行**，**在它上方加一整块控件带**。
两侧的增量都是按记录变的，所以**哪一侧都造不出另一侧**。

剩下唯一诚实的做法：**同一个纯函数同时作用在两侧**，要求余下部分逐字节相同 ——
把「基线里那块控件带」（本来就不存在）和「候选里那几行参数」（本来就已删掉）都按声明删掉，
再比。代价与 `delete` 相同，并且**写在 NC13 里而不是藏起来**：被从两侧同时删掉的东西**不在比较范围内**，
所以那块载荷的**内容**由覆盖断言拥有、**形状**由 `scoped` 拥有、**位置**由 `order` 拥有。

`applies: 84`（候选侧）与 `applies_base: 66`（基线侧）**分开声明**：
`symmetric` 用一个数会让「删新增块的函数在基线上什么也没找到」和「删旧行的函数在候选上全找到了」
两件事互相抵消。基线 66 = 42 页里那些**真有**参数行的页 × 各自行数，候选 84 = 42 页的控件带 + 脚本 + 载体。

**本批另外修好了一条会静默变绿的判据**：`insert` 分支上一度残留 `mask(act)`，
而在这个分支上 `act` 就是**变换后的基线** ⇒ 等于拿基线和自己比，候选一个字节都没读。
它失败时是**红**的（不是绿），所以带着它的 H7c 仍然通过（H7c 走 `delete` 分支），
但 H7a／H7b 会**证明不了任何事**。已恢复为 `mask(b)`，并补 **NC16**：
`insert` 方向必须**拒绝**一个未被施加变换的候选，且**接受**一个真实的候选（两半都在，自带数据）。

修复后这几条断言被**重构**，两处口径改动值得记下来：

- 叠层这一条从「写出 96 这个数」改成**不变式**：抽屉必须高过**页面当下摆出的每一个固定层，

1. `--allow-file` 原先是**替换**默认三件而不是**追加**，与它自己的帮助文字相反。

2. 函数**集合相等**比原来的「一段连续块里含有那个符号」更紧，于是当场抓出**两处声明不全**：
   H7d 没声明它改动的两个 JS 文件、H7c 没声明它新增的第二个函数（`…_specs_table_chips`）。
   补齐后两侧都过。**这不是工具坏了，是工具在工作** —— NC7 就是盯着这一条的（塞一个未声明的函数 ⇒ 必须失败）。

4. **字符预算 → 结构性边界**：「抽屉只在手机段里脱离文档流」原先写成 `@media (max-width: 768px) \{[\s\S]{0,900}…`，

## 5. 本批修正的一个产品缺陷（已提交，`712b01f`）

**渲染出「Per per bottle」**：20 个 pack 页的提示读成 `Per per bottle`。

根因是**一个字符串被当成两个东西用**：`hint` 既要当选项上方的提示语，又要被邮件侧用
`substr($group['hint'], 4)` **回头切出**单位短语 —— 而 `sinofresh_formula_pack_parts()` 的尾巴
本来就从第一个非数字字符开始（带着介词），所以 `substr(…,4)` **碰巧永远是对的**，
只有从渲染结果读才能看出重复。改成两个字符串：

```php
'hint'        => $pack_tail !== '' ? ucfirst($pack_tail) : 'Choose one or more',
'unit_phrase' => $pack_tail,
```
```php
if ($group['label'] === 'Pack Size' && !empty($group['unit_phrase'])) {
    $rows[$group['label']] .= ' ' . $group['unit_phrase'];
}
```

判为**修复**而不是升级为停机问题：它是本批自己新写的字符串、**不改数据**、**不改方向**、且只有一个正确写法。
覆盖断言现在**点名**这个错（`sf-fdetail-config__hint">Per per ` 必须为 0），
因为「提示有多少条」这种计数**看不见一个重复的词**。

## 6. ⛔ 停机过的产品缺陷：抽屉的叠层（裁决＝修法 A，已落地）

### 6.1 停机时的实测（420×900，抽屉打开；原始记录 `_backup/b2d-h7d-banner-before.json`）

| 层 | 层级 | 盒子（420 宽屏） | 对抽屉做了什么 |
|---|---|---|---|
| `header.sf-header.is-sticky` | `z-index: 999` | y 0–57 | 盖住抽屉顶部 **y0–54** |
| `nav.trp-language-switcher.trp-floating-switcher`（TranslatePress 浮动切换器） | `position:fixed; z-index: 99999` | x 250–378，y 845–900 | 盖住 Done 右段 **x267–362** |
| `.sf-cookie-banner` | `z-index: 9999` | y 634–900（高 266） | 盖住底部 **y648–882** |
| **本批新增的抽屉** | 列表 `z-index: 96`，出口 `z-index: 97` | 出口 380×40 @ y840–880 | —— |

- **横幅在的时候**：Done 按钮中线上 **19/19 点全被盖住**；`(210,860)` 这个像素属于 `sf-cookie-banner__manage`。
  ⇒ **第一次来的手机访客打不开也关不上抽屉**：唯一的出口在横幅底下。仍可恢复（点横幅自己的按钮答复后即可），
  Escape 也可用（但那要有键盘），所以不是死胡同 —— 但看起来就是一个坏掉的覆盖层。
- **横幅答复之后**：出口中心可点（`sf-fdetail-config__close`），但右边 **6/19** 仍被浮动语言切换器盖住。

### 6.2 这不是「碰巧」，是本批忽略了站内的既有约定

样式表里**每一层全屏覆盖都在 ≥9998**，而且注释里写着它们各自为什么在那个位置：

```
.sf-header.is-sticky      999
.sf-toc                  9990   /* 在浮动栈（9998）之下 */
.sf-progress             9995   /* 在吸顶头部（999）之上、在浮动栈（9998）之下 */
.sf-float-stack          9998
.sf-toast                9999
.sf-cookie-banner        9999   /* 固定底部条 */
.sf-inquiry-modal       10000 / 10010（移动端）
.sf-basket-drawer       10001
.sf-certmodal           10010
.sf-lb                  99999
─── 本批的抽屉 ───
.sf-fdetail-config--open .sf-fdetail-config__list   96
.sf-fdetail-config--open .sf-fdetail-config__close  97
```

**抽屉是全站唯一低于 999 的覆盖层**，而它是**满屏**的。提交信息与扫描档里**都没有关于 96/97 的理由**
（已核对 `git show 09cdf80 -- style.css`），所以这是一个**未经审视的取值**，不是设计决定。
对照：同样从页面弹出的询盘弹窗在 10000/10010、关闭按钮在右上角，所以它既压得住横幅也不受横幅影响。

### 6.3 三个候选修法与裁决

- **A（建议，已采纳）**：把抽屉抬到站内其余全屏层同族的高度。**一行**改动，三个穿透一起消失，
  并回到既有约定（覆盖层在横幅之上）。代价：抽屉打开期间语言切换器不可用（横幅本来就该被盖住）。
- **B**：把出口挪到抽屉**顶部**（如右上角 X），顶部再给吸顶头部留出空档。
  解决「顶部被穿透」与「出口被盖住」，但底部横幅仍压着抽屉**内容**（内容可滚动，因此不致命），
  且不再是「一个按钮说完」的设计 —— 抽屉里要同时有顶部的 X 和底部的 Done 时，得再决定留哪个。
- **C**：不动层级，改成抽屉打开时**临时隐藏**横幅与浮动切换器（关闭后恢复）。
  改动面最大，多出一份「开→关」的状态要维护，属于新交互而不是修 bug。

**当时停在这里的理由**：修法 A 的取值与「抽屉打开时语言切换器该不该仍可用」都是**产品判断**，
而裁决规则写明「门抓到产品 bug ⇒ 停」。**用户裁决：按 A 做。**

### 6.4 落地：取值为什么是 `100000`，以及它到底修好了什么

```diff
 	.sf-fdetail-config--open .sf-fdetail-config__list {
 		display: block;
 		position: fixed;
 		inset: 0;
-		z-index: 96;
+		z-index: 100000;
```

- **不是 10002、也不是 10010**：必须**高过 99999**，因为压住出口右段的浮动语言切换器来自
  TranslatePress 自己的样式表（`trp` 在 `style.css` 里零命中），主题**改不了它、只能压过它**。
- **为什么是「顶之上一步」而不是一个更大的数**：站内栈顶是灯箱的 `99999`，取 100000 就是
  **一步**、没有留下让人随手再插值的空档。**灯箱与抽屉永远不会同时在场** ——
  满屏不透明的抽屉盖住时，底下的图片根本点不开，所以这一步不花任何代价。
- **出口的 97 不动**，并在样式表里写明理由：`config.js` 把出口 `appendChild` 到列表**里面**，
  列表自己的 `z-index` 就是叠层上下文，出口的数字只在那个上下文内部排序。
  **把它一起抬高会暗示两者是兄弟节点**，那才是真的错。
- **代价说清楚**：抽屉打开期间，横幅与语言切换器都在它下面（横幅本来就该被盖住）。
  抽屉自带出口，所以这不是把访客关在里面。

**修好后同一探针的实测**：出口覆盖 **0/60**（原 16/60）、抽屉被穿透 **0/25 行**（原 10/25）、
连续带 **`[]`**、`(210,860)` 这个像素属于 `sf-fdetail-config__close`；抽屉 `z-index` 实测 `100000`。
`docs/batchH7d-shots/h7d-07-phone-layers.png` 是这一态的帧（抽屉底部、横幅原本占的那一段）。
