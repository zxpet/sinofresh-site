## 一、要解决什么（一句话）

「Get a Quote」表单（form 8）10-10 起被同一台机器人以慢速滴灌方式刷入 210 条垃圾，连带向被滥用的第三方邮箱发出 412 封本域名邮件。目标是**止住垃圾**，同时**不误伤真客户**，并把「按真实 IP 限流/取证」这条能力链修通。

## 二、为什么现有三层防护都没起作用（决定方案的三个事实）

| # | 事实（实测） | 对方案的含义 |
|---|---|---|
| 1 | Fluent Forms 的 `resolveIp()` **不信任任何代理**（`config/trustedproxy.php` 不存在）⇒ 存的是 **CF 边缘 IP** | ⛔ **不修这一条，任何「按 IP 限流」都是按边缘节点计数**——它挡不住慢速机器人（30 秒滑窗最大提交数 = 1，阈值 5），反而会在收紧阈值时**先挡住共用同一边缘节点的真客户** |
| 2 | 内置洪泛控制是「30 秒内 ≥5 次」型，机器人平均间隔 5205 秒 | ⛔ **调参救不了**，需要与威胁模型匹配的层（人机验证 / 内容判定 / 长窗口计数） |
| 3 | WP nonce 对未登录访客是**12 小时内的常量**（212 条提交只有 9 个不同 nonce） | ⛔ **nonce 不是防护**；同理「加隐藏字段 + 时间戳」类前端技巧对会读 DOM 的机器人无效 |

补充一条**正面**对照：同服务器上的自研端点 `POST /wp-json/sinofresh/v1/inquiry` **已经**有真实 IP + 蜜罐 + 计时陷阱（H11 成果）⇒ 本轮 **0 条**垃圾。**证明了有效配置长什么样**，也是本方案的设计蓝本。

## 三、三个方案

### 方案 A — 只动 Fluent Forms 后台（最小面、当天见效）

| 层 | 动作 | 位置 |
|---|---|---|
| A1 | 打开**蜜罐** | FF → Global Settings → Security（键 `_fluentform_global_form_settings.misc.honeypotStatus`，UI 文案「Enable Honeypot Security」）；若界面无开关则 `wp option patch insert … misc honeypotStatus yes` |
| A2 | 给 **form 8** 加 **Cloudflare Turnstile** 字段 | 先在 CF 面板建 Turnstile widget（**免费、无限量**）拿 siteKey/secretKey → FF Global Settings → Security → Turnstile 填密钥 → 表单编辑器把 Turnstile 组件拖进 form 8 |
| A3 | 打开 form 8 的「**拒绝空提交**」 | 表单设置 → Restrictions → Deny Empty Submission |

- **改动面**：纯后台设置，**零代码、零服务器配置、零主题改动**
- **效果**：Turnstile 对脚本化提交是**硬阻断**（机器人过不了挑战）；蜜罐拦掉不解析 DOM 的低级机器人
- **致命缺口**：真实 IP 仍拿不到 ⇒ **取证、按 IP 封禁、按 IP 限流、访客统计全部不可用**；直连旁路的洞仍在
- **风险**：低。⚠️ 唯一要提前想好的是 **CF 侧故障兜底**（见 §五-3）
- **代价**：CF 面板 5 分钟 + FF 后台 10 分钟；**不需要 dev/生产分别过门**（无代码）

### 方案 B — 方案 A + 根因修复 + 存量清理（**推荐**）

在 A 之上加：

| 层 | 动作 | 形式 |

- **收益链（B1 的连带价值，不止于表单）**：

## 四、内容兜底规则（B3 的具体设计）

**采用「高精度、宁可漏放不可误杀」原则**。本批观测到的机器人特征：

| 规则 | 判据 | 误杀风险 |
|---|---|---|
| R1 | `company_name_1` 匹配 `^[A-Z][a-z]{2,10}Ton$`（本批 206/212 命中） | 极低（真人公司名不会是这个形态）——**作为 v1 的主规则** |
| R2 | `contact_person_2` 匹配 `TonGM$` | 极低 |
| R3 | `notes_10` 命中「同一句模板的多语种译文」指纹（本批 30+ 语种同一句） | 低（先只记录告警、不拒收，攒样本后再决定是否升级为拒收） |

⛔ **明确不做的规则（会误杀真客户）**：

- ❌ **邮箱域名黑名单**。本批被滥用的域名里 `t-online.de`(34) / `web.de`(13) / `gmx.net` / `libero.it` / `alice.it` **全部是德国与意大利真实客户的主流邮箱服务商**。按域名封 = 直接砍掉德语区客户。
- ❌ 「非英语/非德语内容即拒收」。站上真客户会发俄语、阿拉伯语、日语询盘。
- ❌ 「UA 陈旧即拒收」。老旧设备/企业代理会误伤；**只作为告警信号**。
- ❌ 「同 IP 短窗口多提交即封 IP」。在真实 IP 修好前，这条**打的是边缘节点**。

## 五、必须一并决策的三件事

### 1. 存量 210 条怎么处理
建议：**先全量导出**为 `docs/h24-spam-archive-2026-10-12.json`（含 id/时间/全部字段/IP，供日后核对与统计），再批量把 `status` 置为 `trashed`（**不 DELETE**）。
理由：`sales@zxpet.com` 的收件箱与后台列表要立刻清爽；数据留档以备复盘「损失了多少真询盘」。

### 2. 「自动回复客户」要不要先关
它是**这台机器人的放大器**：1 条垃圾 = 1 封发给陌生第三方的本域名邮件（3 天 412 封，含政府/机构域名）。
建议：**保留功能，但在防护落地前先临时停用**（FF → form 8 → Settings & Integrations → Notifications → 关闭「Auto Reply to Customer」），防护验收通过后**立即恢复**。
备选：不做临时停用，但要求防护在 24 小时内落地。

### 3. 验证码供应商：Turnstile vs reCAPTCHA（可用性已实测，不再需要你确认网络）

- **Turnstile**（推荐）：CF 原生、**免费无限量**、与我们已在用的 CF 同一后台、隐私友好（站上已有 consent 体系，GDPR 语境更稳）、无需 Google 账号
- **reCAPTCHA**：生态成熟，但在 GDPR 语境下是已知争议点，且需要额外 Google 账号

**可达性已实测（本轮，两个位置各测一次）**：

| 测试位置 | 结果 |
|---|---|
| 中国大陆（本机 Mac） | `challenges.cloudflare.com/turnstile/v0/api.js` → 跟随重定向 **HTTP 200 / 86 732 B / 2.22 s**，首字节是真实 JS（非拦截页） |
| 源站（`65.49.215.152`） | 同一地址 **HTTP 200 / 86 732 B / 0.056 s** |

⇒ **挑战脚本在国内与源站两侧都能正常加载**，此前担心的「国内验收加载不出控件」不成立。
（附带实测：本机 GET `https://www.zxpet.com/` 20 秒超时而 `HEAD` 正常返回 CF 响应头——这是本项目已知的「本机→CF 边缘超时」现象。**故本批前台验收仍按既定纪律在服务器侧执行**，与网络问题无关。）

### 4. 兜底：CF 侧故障时表单会不会全线失效
Turnstile 校验失败 ⇒ FF 直接拒收 ⇒ **CF 侧故障期间所有询盘丢失**。三档兜底（按代价从低到高）：
- (a) 接受（Turnstile 可用性 SLA 高，且失败可观测）
- (b) mu-plugin 里加「Turnstile 服务连续不可用 ⇒ 自动降级为 蜜罐 + 内容规则」（**推荐**，代价约 20 行）
- (c) 双验证码供应商切换（过度设计，不建议）

## 六、验收计划（沿用本项目纪律：门 + 负对照 + 不新增红）

**首要验收标准是「真人不被误伤」**，其次才是「垃圾被挡」。

| # | 验收项 | 方法 | 判据 |
|---|---|---|---|
| ① | **真人路径（正向）** | 浏览器（Playwright，dev）真实填表提交 form 8 | **200 / 入库成功 / 收到管理通知**；改前改后各跑一次 |
| ② | **机器人路径（反向）** | 脚本直接 POST `admin-ajax.php?action=fluentform_submit`（不带/伪造 Turnstile token、蜜罐填值、命中 R1 的名称） | **被拒**（400/422），且**不入库** |
| ③ | 真实 IP 生效 | 提交后读 `wp_fluentform_submissions.ip` | **不等于** CF 边缘 IP；与 `CF-Connecting-IP` 一致（构造用例自证，不依赖运营数据） |
| ④ | 限流生效 | 同一真实 IP 连发 4 次（构造用例） | 第 4 次 429；**换 IP 后第 1 次成功**（证明键是真实 IP 而非边缘 IP） |
| ⑤ | 直连伪造防护 | 直连源站并**伪造** `CF-Connecting-IP: 1.2.3.4` | 记录到的 IP = **真实连接 IP**，不是 `1.2.3.4`（证明信任判断生效） |
| ⑥ | 门 | 新 `tools/h24_gate.py --source` / `--live`（dev + 生产） | 全绿且**双向负对照**：把设置/插件回退 ⇒ 对应断言转红 |
| ⑦ | 不新增红 | h9/h10/h11/h12/h13/h14/h18/h18c/h19/h23 兄弟门复跑 | 红集合与各自汇总行一致 |
| ⑧ | 邮件侧 | 提交被拒时 | **不发信**（管理通知与自动回复都不发） |
| ⑨ | 冷却观察 | 上线后 24h / 72h 读一次提交与邮件量 | 垃圾归零或近零，**真询盘仍有**（对照：改造前日均真询盘基线） |

## 十四、运行期发现（5 条，含 2 条对既有结论的更正）

1. **⚠️ 更正：`wp-mail-logging` 在生产是 `active`（1.16.0），此前「该表已废弃」的结论有误。**
   - 事实：生产同一封邮件**两张表都记**（`wp_fsmpt_email_logs` + `wp_wpml_mails`）；dev 侧该插件为 `inactive`，只有前者记录。
   - 影响：**dev 上成立的「历史表保持不动」断言搬到生产必然误报**（L4 首跑即因此挂了 2 项）。凡「零发信」类举证，生产必须**两表同时断言**。
   - 表结构差异：`wp_wpml_mails` 的收件人列名是 **`receiver`**（不是 `to`），主键是 **`mail_id`**。

2. **`wp_sf_form_spam_log` 的生产建表时机**：`sf_fg_maybe_install()` 原只挂 `admin_init` + 拦截时惰性调用。生产部署后既未登录后台、也尚无拦截 ⇒ **表不存在**，首次拦截会在**请求处理路径里**跑 `require upgrade.php` + `dbDelta`（违背"不在请求处理器做重活"）。**处置：部署阶段主动预热**（`wp eval 'sf_fg_maybe_install();'`），已建表且 15 列与 dev 完全一致。

3. **自动回复停用前仍在放血**：生产 `wp_fsmpt_email_logs` 显示 10-12 06:19 / 06:25 / 06:37（WP 本地时间 UTC+8）三轮机器人提交，每轮都发出 **「管理员通知 + 自动回复」两封**（收件人是被滥用的 `gianpiero.logiudice@alice.it` 等第三方）。最新真实垃圾提交（06:37）比 form-guard 安装（02:38 UTC = 10:38 本地）**早 1 分钟** ⇒ 生产尚未经历"装上防护后的真实机器人流量"。

4. **拦截器绕过 FF 限流（已知的设计取舍，非缺陷）**：拦截器优先级 5 早于 FF 处理器，被拦提交根本不进入 FF，因此**不消耗** FF 的 `max_submission_count` 配额（计数查的是 `fluentform_submissions`）。这带来一个可被利用的点：机器人若持续被拦，可以无限次提交而不触发 429 限流（但每次都零发信、只多一条 spam 行 + 一条审计行）。**当前判定为可接受**（本地/服务端计算成本极低，且 spam 落库消息队列是用户明确要求的），但需在 §十六 观察 spam 表增长速度。

5. **生产写测试的「零污染」实现**（可复用范式）：
   - 邮件隔离用**条件式**夹具（仅当请求带 `X-SF-H24-Test` 头才改写收件人）⇒ **测试窗口内真实访客的邮件完全不受影响**（比 dev 的无条件夹具更安全）；
   - 清理用「**基线 max id 快照 + 来源限定**」（提交行限 `ip LIKE '%127.0.0.1%'`、邮件限 `receiver='h24-test@invalid.example'`）⇒ 即使测试窗口内恰有真实访客提交，也**不会被误删**；
   - 测试夹具以 `trap ... EXIT` 保证**无论成败都删除**。

## 十五、DMARC 中期计划（域名信誉保护，长期）

**背景**：本批根因之一是「1 条垃圾 = 1 封发往陌生第三方的本域名邮件」，3 天累计 412 封，直接消耗域名发信信誉。短期已用「停用自动回复 + 拦截零发信」止血；**中期要提升发信域名的可信度**。

| 阶段 | 动作 | 前置条件 | 验证 |
|---|---|---|---|
| 现状 | DMARC `p=none`（仅观测） | — | 读 DNS TXT |
| **前置 1** | 确认 SPF / DKIM **全部通过** | 自有 SMTP（FluentSMTP）配置稳定 ≥ 1 个完整月；`Authentication-Results` 中 `spf=pass` 且 `dkim=pass` 连续达标 | 抽取发往 Gmail / Outlook / QQ 的头部逐封核对 |
| **前置 2** | 读 DMARC 聚合报告（rua） | 已配置 `rua=` 且收到 ≥ 2 周报告；**「已通过认证」占比 100%**，无未预期来源 | 汇总各来源 IP 与认证结果 |
| 升档 | `p=none` → **`p=quarantine`** | 前置 1、2 均达标 | 升档后观察 7 天，确认无合法邮件进垃圾箱 |
| 观察窗 | 保持 `p=quarantine`，不改 `pct` | — | 监控 `sales@` / `info@` 往返邮件可投递性 |
| 备选升档 | `p=reject` | `p=quarantine` 稳定 ≥ 1 个月且零误伤 | **仅在完全确定后**，且先 `pct=25 → 100` 渐进 |

**⛔ 硬约束**：**在 SPF/DKIM 尚未 100% 通过前，绝不升档**——否则会把自家合法邮件（询盘通知、报价单）一起扔掉，比现在的「信誉放血」损失更大。

**责任归属**：DMARC 升档是**域名/DNS 侧动作**，需在 CF DNS 面板操作（同 C1/C2，属 Sam 本人操作、我方出清单与验收脚本）。
