## 一、扫描结论（全部只读实测，含代码级证据）

### 1. 限流机制的真相（决定 #2 怎么改）

Fluent Forms **6.2.14** 的限流在**两处**实现（`FormHandler::preventMaliciousAttacks()` 与 `FormValidationService::preventMaliciousAttacks()`），计数口径完全相同：

```php
$submissionCount = wpFluent()->table('fluentform_submissions')
    ->where('status', '!=', 'trashed')        // ← spam 行同样计入！
    ->where('ip', $clientIp)
    ->where('created_at', '>=', $interval)
    ->count();
if ($submissionCount >= $maxSubmissionCount) → 429 Too Many Requests
```

| 事实 | 值 |
|---|---|
| 插件默认 | `max_submission_count = 5` / `min_submission_interval = 30`（秒） |
| **我们当前覆写** | **`3` / `3600`**（`SF_FG_MAX_SUBMISSIONS` / `SF_FG_MIN_INTERVAL`） |
| 计数对象 | 该 IP 在窗口内**所有 `status != 'trashed'` 的记录**（含我们写入的 `spam` 行） |
| IP 取值 | `$this->app->request->getIp()` → 走 `REMOTE_ADDR`；`zz-sf-aa-real-ip.php` 已把它归一为**真实访客 IP**（这层是对的） |

**结论（两条都需要修）**：
1. **误伤真客户**：同一出口 IP（企业 NAT / 展会 WiFi）连发 **3 条**即被挡；跨境客户一天内二次询价会被挡。
2. **计数被污染**：机器人被我们拦下后写入的 `spam` 行**会挤占真客户的配额**——同一个 IP 上机器人刷 3 条，真客户第 4 条就被 429。

### 2. Turnstile 现状（#1）

- `_fluentform_turnstile_details` 选项在**生产与 dev 都不存在**（`wp option get` 报 Does it exist?）⇒ `sf_fg_ts_enabled()` 恒 `false` ⇒ **当前只有降级分支被执行，实际防护未启用**（与你的判断完全一致）。
- 自管链路**已在位且完整**：

| 环节 | 函数 | 现状 |
|---|---|---|
| 取密钥 | `sf_fg_turnstile_keys()` | 读 FF 的 `_fluentform_turnstile_details` → 为空返回 `[]` |
| 健康探测 | `sf_fg_turnstile_probe()` + `sf_fg_turnstile_schedule()` | 15 分钟一次；**连续 3 次失败**才判不健康 |
| 总开关 | `sf_fg_ts_enabled()` | = 有密钥 ∧ 服务健康 ∧ 防护总开关开 |
| 前端注入 | `sf_fg_print_footer_script()` → `injectTurnstile()` | 脚本 `onerror`／6s 超时 ⇒ **不插 widget，表单照常可提交** |
| 服务端校验 | `sf_fg_ts_verify()` 三态 | `true` 通过 / `false` 明确失败 / `null` 不可达 |
| 状态归并 | `sf_fg_ts_state()` | `disabled` / `absent` / `ok` / `fail` / `degraded` |
| 折分 | `sf_fg_signal_turnstile()` | **仅 `fail` = +4**；其余一律 0 |
| FF 侧兜底 | `sf_fg_disable_captcha()` | Turnstile 不健康时让 FF 原生 captcha 也跳过 |

- ⚠️ **密钥存储位置必须改**：FF 的 captcha 有独立开关 `_fluentform_turnstile_keys_status`。若经 **FF 后台**填写密钥，FF 会**自己再渲染一个 Turnstile widget**，并走它「校验失败 ⇒ 抛 422 ⇒ 硬拒提交」的链路——**那正是你要求避免的"真客户填不了表"**。
  ⇒ 建议改用**我们自己的选项** `sf_fg_turnstile_keys`（`sf_fg_turnstile_keys()` 先读自己的、为空才回退 FF 的键，保持兼容）。**FF 后台的 captcha 保持关闭不动。**

- ⚠️ **CSP 需同步补白名单**：源站现为 `Content-Security-Policy-Report-Only`（**只报告、不拦截**，所以现在启用 Turnstile 不会被挡），但策略里**没有** `challenges.cloudflare.com`：

```
default-src 'self';
script-src  'self' 'unsafe-inline' https://static.cloudflareinsights.com;    ← 需加 https://challenges.cloudflare.com
style-src   'self' 'unsafe-inline';
img-src     'self' data: https://i.ytimg.com;
frame-src   https://www.youtube-nocookie.com;                                ← 需加 https://challenges.cloudflare.com
connect-src 'self' https://cloudflareinsights.com;                           ← 需加 https://challenges.cloudflare.com
base-uri 'self'; form-action 'self'; object-src 'none'
```

  Turnstile 的 widget 是 iframe + 脚本 + XHR，**三个指令都要**。本批一并补进这份 Report-Only 策略（零拦截风险），避免将来转强制时才发现。

- ⚠️ **启用后每次提交多一次外呼**：`sf_fg_intercept()` 在评分**之前**调用 `sf_fg_ts_state()` → `sf_fg_ts_verify()` 会 POST 到 CF（当前超时 **5s**），在**请求路径内**。健康探测判不健康时 `ts_enabled()` 直接 `false`⇒不再外呼（已有兜底）。**建议把超时 5s → 3s**，进一步压低最坏延迟。

### 4. 后台复核入口（#4）—— 三项逐条实测

| 你的要求 | 实测现状 | 判定 |
|---|---|---|
| **菜单位置明显** | 顶级菜单「表单防护」，`manage_options`，`dashicons-shield-alt`，位置 `58` | ✅ **已满足**（可再优化） |

### ② 限流改造（推荐"范式 B"）

**范式 A（最小改动）**：只把 `SF_FG_MAX_SUBMISSIONS` 3 → **5**，仍由 FF 计数。
- 优点：一行改动。缺点：**spam 行仍计入**、计数语义依旧不干净，只是把误伤点从 3 推到 5。

**范式 B（推荐 = 你说的"更好"那档）**：关闭 FF 的 IP 限流，改由我们自建计数。

```
fluentform/prevent_malicious_attacks → false（仅对受保护表单，防护总开关关掉时自动恢复原行为）

自建限流（在 sf_fg_intercept 内，评分之前）：
  ① 真实提交计数（status NOT IN ('spam','trashed') 且 ip = X 且 1h 内）
       ≥ SF_FG_REAL_MAX_PER_HOUR（默认 5） ⇒ 429
       —— 直接落地你的"放宽到 5 次/3600"
  ② 被拦计数（审计表 wp_sf_form_spam_log 且 ip = X 且 24h 内）
       ≥ SF_FG_ABUSE_429（默认 20） ⇒ 429（省掉评分开销）
       ≥ SF_FG_ABUSE_AUTOBLOCK（默认 50） ⇒ 自动加黑名单（你的保险项）
  ③ spam 行**不进入** ① 的计数 ⇒ 真正实现"只有被拦的才计数"
```

- 优点：**消除真客户被挡**；spam 不污染真实配额；顺手落地黑名单保险。
- 代价：改动较大，需新增门与回归（我会补 `h24b_gate.py`）。
- 兜底：即使真实限流被绕过，仍有评分 + 黑名单 + 自动加黑三层。

**回滚**：把 `sf_fg_enabled` 置 `0` 即整体恢复 FF 原行为（含原 30s/5 次默认）。

### ③ 审计保留期 + 告警带行数

| 项 | 设计 |
|---|---|
| 常量 | `SF_FG_LOG_RETENTION_DAYS = 90`，过滤器 `sf_fg_log_retention_days` |
| 任务 | 新增 `sf_fg_log_cleanup()`，挂 **每日** cron（`sf_fg_log_cleanup_event`） |
| 幂等 | 记录 `sf_fg_log_cleanup_last`（时间戳），同日不重复跑，并记录删除行数 |
| 保留 | 删 `wp_sf_form_spam_log` 中 `created_at < now - 90d` 的行 |
| 告警 | `sf_fg_send_alert()` 正文追加两行：**审计表总行数**、**24h 内被拦数**；并把 24h 内触发自动加黑的 IP 列出（若有） |
| 展示 | 「表单防护」页状态行加「审计表行数 / 最近清理时间 / 下次清理」 |

> **附议（待你决定，可放本批也可放下一批）**：`wp_fluentform_submissions` 里 `status='spam'` 的行同样会无限增长（且会长进 FF 条目列表）。建议对 **>90 天的 spam 行自动 `trashed`**（沿用你"先标记不 DELETE"的偏好，不物理删除）。**默认不做**，等你点头。

### ⑥ 黑名单保险（24h > 50 自动加黑）

```
在 sf_fg_intercept 落库+审计之后：
  n = 审计表中该 IP 24h 内行数
  if (n >= SF_FG_ABUSE_AUTOBLOCK(=50)) 且 该 IP 尚未在黑名单:
      sf_fg_blocklist_add('ip', $ip, 'auto:50/24h')
      → 并入当日告警邮件正文；后台复核页显示 note
```

- 幂等：已存在则不重复加。
- 安全：只对**已被评分/黑名单拦下过**的 IP 生效（**真实客户永不计入**，因为它们不进审计表）。

### ⑦ C 组边缘加固（仅排期，本轮不动手）

24h 观察窗结束、B 档稳定后**单独开窗口**：
- C1 WAF 四条规则 + Bot Fight Mode（**Sam 面板手动**，清单见 `docs/h21-cloudflare-waf-rules-2026-10-06.md`）

## 四、约束与纪律（本批沿用）

1. **必须在服务器上跑 HTTP 验收**：本机 → CF 边缘 25–40s 超时是已知现象，会打出假 FAIL。
2. **生产写测试零污染**：条件式邮件隔离（`X-SF-H24-Test` 头）+ 基线 max id 快照 + 来源限定清理 + `trap EXIT`。
3. **部署纪律**：scp → 服务器 `php -l` → md5 三方一致 → 原子 `install -o apache -g apache -m 644`；**改主题/插件必 bump 版本**（本批不涉主题 CSS，故不必 bump 主题版本）。
4. **"零发信"举证两表同查**（若 Q4 选 A，则本条在停用后改为单表 + 历史区间说明）。
5. **断言纪律**：先读代码再写断言；每条断言配 negative control；不得对运营数据写断言。
6. **`wp eval-file` 非全局作用域** ⇒ 计数器一律用 `$GLOBALS[...]`。
7. **macOS 无 `timeout`**；BSD grep 用 `-E`。
